# StudyPi 产品设计 v0.1

状态：设计提案。除项目入口中列明的提示词基础，其余能力尚未实现。
首版对象：有持续学习目标、会阅读材料并做练习或实验的个人用户。

## 1. 核心体验

一个学习项目包含：目标、已有基础、原始材料、待解问题、进行中的任务、学习证据和成果。
用户可以只问一个问题，也可以逐步积累成几周的研究项目。

首个完整使用案例：

> 我想理解工作记忆理论，提供两份论文和一章教材。先帮助我比较观点，再设计一个可以运行的小实验，最后让我尝试解释结果。

1. 建立目标和材料目录，保留文档版本、页码及章节定位。
2. 根据当前请求选择解释或研究路径；背景足够时直接开始。
3. 从原文提取支持与反驳证据，呈现不同理论的假设和适用条件。
4. 用户可以停下来问一个概念，也可以让工具在选定环境执行模拟。
5. 输出带来源的比较笔记、可重复的实验文件和尚未解决的问题。
6. 用户自愿解释一个结果，系统据此记录本次理解表现，建议下一步或后续复习。

这个流程应当可以暂停、改目标、重新运行某一步，也可以在手机上离线查看已有成果。

## 2. Soul：把思想变成可观察的行为

Soul 是稳定且可评估的行为原则。哲学与教育理论用于形成判断习惯，不要求模型扮演某位名人，
也不要求在每次回复中展示一套理论名词。

| 思想来源 | 对应行为 | 反例与约束 |
| --- | --- | --- |
| 可错论、批判理性 | 说明前提，允许被新证据纠正，主动寻找反例 | 模型自信不能替代证据 |
| 实用主义与探究 | 用问题、实验和行动检验理解 | 做出产物不自动代表学会 |
| 苏格拉底式追问 | 在练习或辨析时用一个关键问题暴露假设 | 用户请求讲解时直接解释，不强迫猜答案 |
| 支架教学、认知学徒制 | 示范 → 共同完成 → 减少帮助 → 独立应用 | 帮助量随表现调整，不固定为“试两次” |
| 建构与认知负荷视角 | 连接先备知识，控制步长，配合具体例子 | 不推断固定“学习风格”或人格类型 |
| 元认知 | 区分理解感、信心与实际表现，让用户检查推理 | 不依据聊天频率打出精确掌握百分比 |
| 形成性评价 | 对具体错误给可行动反馈，再观察改进 | 不用抽象表扬或能力标签替代反馈 |
| 工程中的可复现与闭环 | 写清输入、方法、结果、限制与验收条件 | 未运行的代码不报告成实验结果 |
| 关怀与自主 | 尊重时间、选择权和节奏，逐步减少对助手的依赖 | 不以焦虑、羞辱或连续签到维持使用 |

ICAP 将学习参与区分为被动、主动、建构和互动，并提出可检验的学习效果假设。
我们据此设计复述、解释和共同推理活动；这只是产品设计依据，不能当作 StudyPi 已被证明有效。
[原始论文](https://doi.org/10.1080/00461520.2014.965823)。

提示词按层加载：稳定 Soul → 场景策略 → 当前目标与学习证据 → 有关材料 → 工具与环境能力 → 本轮请求。
首阶段只接入稳定 Soul 和现有引导学习卡片；结构化学习上下文需要后续存储与工具支持。

## 3. 五条首版学习路径

| 路径 | 何时选用 | 主要交付 | 是否等待用户作答 |
| --- | --- | --- | --- |
| 概念讲解 | 理解一个概念、公式、论证 | 解释、例子、反例、关联来源 | 通常不必 |
| 引导练习 | 用户想自己完成或发现错误 | 分层提示、反馈、独立尝试记录 | 是，按关键步骤 |
| 深度研究 | 比较观点、读论文、查证 | 问题分解、证据表、综合结论和缺口 | 有关键歧义时 |
| 计算与实验 | 验证猜想、分析数据、编程学习 | 代码、数据、运行结果、可复现记录 | 涉及目标或资源取舍时 |
| 复盘与复习 | 巩固已学内容、纠正误解 | 检索练习、迁移任务、后续建议 | 依据用户选择 |

教学设计为扩展路径：从目标和受众反推活动与评价，使用学习者能够展示的表现作为验收。

## 4. 多模型协作

顶层小模型处理有边界的路由判断，主 agent 对整体教学或研究任务负责。
流程 agent 在确有收益时承担阅读、检索、实验或复核。
简单解释通常一次调用即可完成；复杂研究可并行处理独立材料。

关键约束：

- 用户手动选择优先；同一活动内尽量稳定主模型，避免连续换人式体验。
- 路由结合模态、工具能力、预算、延迟和用户意图，不能只按一句关键词分类。
- 小模型判断不可靠或超时，交回主 agent 判断；它无权扩大工具权限。
- 流程 agent 接收最小任务包，输出结论、依据、方法、局限和产物引用。
- 复核 agent 允许提出异议；主 agent 根据证据处理，不采用简单多数投票。
- 模型选择使用实测能力配置，不把具体厂商或型号写死为永久最优。

## 5. 三种执行位置

用户以学习项目为单位选择：手机 Linux、自己的云端服务器、桌面本机。
手机 Linux 用于轻量脚本、小数据、文件加工；云端用于长任务、大资料、较重实验；桌面用于有完整开发环境的任务。
“在本地执行工具”和“在本地运行语言模型”是两项独立能力，界面需要分别说明。

每个任务显示当前运行位置、进度、费用或资源预算、产物和恢复入口。
切换环境时，先停在可恢复检查点，再传送选定资料与产物并验证环境能力。
手机断网不代表云端任务失败；重新连接时恢复状态与已完成输出。
Android 的应用后台限制需要真机测试，本地任务不能承诺在所有设备锁屏后永久运行。

Pi 的可检查上下文、可组合工具和独立运行核心适合成为 harness 的设计参考。
[作者说明](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)。
Orca 展示了多 agent、远端工作区和移动端跟进的组合方式。
StudyPi 将这些理念用于学习项目、实验分支和研究任务的管理。
[Orca 仓库](https://github.com/stablyai/orca)、[远端任务文档](https://www.onorca.dev/docs/ssh)。

## 7. 值得新增的产品能力

### 学习证据账本

每次练习记录题目、作答、给过的提示、评价标准、结果和时间。
概念状态先采用“未知 / 练习中 / 有独立表现证据 / 需要复习”，同时保留不确定性。
允许用户纠正误判。材料阅读次数与在线时长不直接变成掌握分数。

### 问题与前提图

让用户看见“这个问题依赖什么”“哪些概念仍有分歧”“下一步值得验证什么”。
首版用可编辑的列表和关联，已有真实材料与行为后再考虑图形化知识图谱。

### 观点与证据分开

一条研究结论连接支持材料、反对材料、页码与适用条件。
材料更新或结论被反驳时，标记受影响的笔记和实验解释，避免旧结论默默继续使用。

### 口头解释工作流

用户按住录音解释概念，先确认转写，再评价内容。
把“听错了”和“理解错了”分开；反馈关联具体语句，必要时回听片段。
只拿文本的服务不能可靠评价发音，必须在能力展示中明确这一点。

### 研究与实验分支

从同一材料创建不同假设或方法的分支，比较可复现结果。
每个分支保存自己的数据与输出，主任务决定采纳什么，避免互相覆盖。
普通学习项目无需要求用户理解 Git；代码项目可以使用 Git 工作树实现隔离。

### 可渐退的助手

用户可调帮助量，系统依据表现建议减少提示。
有意义的成功包括用户开始独立完成任务，产品不应以更多对话轮次作为唯一目标。

### 方法技能包

技能描述目标、输入材料、步骤、工具需求、输出和验证方法。
首批聚焦论文精读、概念比较、反例构造、实验复现和解释自己的答案。
能力声明与实测结果分开，不能因技能文件声明有某工具就认为环境具备该能力。

## 8. 界面与 STT

手机优先入口为“项目、资料、复习”，账号从个人入口进入。
项目内保留“讨论、材料、任务、成果”视图；输入区始终可以看到学习方式和运行位置。
复杂控制按需展开，常用动作保持一到两步可达。
桌面使用项目导航、当前任务、资料/产物三个区域，复用领域状态而非强行复用整页布局。

STT 接口统一表达：待机、连接、录音、中间转写、最终转写、错误与取消。
记录支持的平台、语言、实时/批量、离线、时间戳、说话人区分、词表与最大音频限制。
这些字段按实际服务提供；没有数据时显示不可用，不能伪造置信度或时间戳。
语音错误后保留草稿，蓝牙切换、权限撤回、来电与后台中断都需要可恢复路径。

## 9. 账号与品牌

StudyPi 是工作名称。建议 Android 发行标识为 `io.github.yubowen050929.studypi`，
正式切换在首次 StudyPi APK 里程碑执行，连同 FileProvider、深链、签名、更新源与备份标识一起核对。
图标方向：抽象的开放书页、探索路径与 π，保证小尺寸、深浅背景和 Android 自适应图标下可辨识。
最终图形需要单独制作并预览，不把概念草图当成已完成的发行资产。

账号的价值是跨设备延续学习：项目同步、运行主机配对、设备撤销和数据导出。
用户的模型供应商账号与 StudyPi 身份属于不同层；保存供应商令牌不等于已经具备产品账号体系。

## 10. 首版范围取舍

先打通“材料 → 讲解/研究 → 可追溯产物 → 一次可选理解验证”的纵向流程。
课程商城、社交排行榜、家长监控、大型机构管理和自动教学有效性评分暂不进入首版。
后续是否扩展，用真实使用中的问题与表现决定。
